## 2026-10-18 — spec: sdd/v2-compat/spec (config V2-nativa de opencode 2.0.x)

topic: sdd/v2-compat/spec
**Goal:** emitir config V2-nativa que en OpenCode 2.0.x reproduzca el comportamiento efectivo de V1, sin romper el anti-drift raíz↔`templates/`, `--upgrade` (preserva `model:` por agente), cero deps runtime ni `npm test`.
**Contexto (investigación):** OpenCode V2 es la línea estable actual (`@opencode/cli` 2.0.x; última `2.0.32` 16-oct-2026); comparte el comando `opencode` con V1 y **no coexisten**. Acepta config V1 pero renombra/ignora claves: `subagent_depth` (ignorado), `permission`+`permission.bash`→`permissions` (array `{action,resource,effect}`; acciones `shell`/`subagent`/`edit`), `agent`/`command`→`agents`/`commands`, `subtask`→`subagent`, `mcp`→`mcp.servers`, `skills` array plano, modelo `provider/model#variant` (el `MODEL_RE` no admite `#`), `external_directory` default V1 `ask`→V2 `allow`. Layout `.opencode/agents|commands|skills/` y `SKILL.md` sin cambios; los breaking de V2 (plugins, server/client API, `tui.json`) no los usa el harness. La fuente tiene contradicciones (mirrors antiguos decían "2.0 beta") → todo queda condicionado a verificación empírica.
**Gate 0 (BLOQUEANTE, primera task):** config V2 mínima escrita a mano en dir temporal + `@opencode/cli` 2.0.x; `opencode --version` y `opencode debug config` (si existe en 2.0.32); capturar prueba de (a) sin warnings por claves del harness, (b) `default_agent` resuelto, (c) `instructions`/`AGENTS.md` resuelto, (d) una regla `deny` y una `ask` efectivamente aplicadas. Ninguna task de migración arranca antes. Si el enforcement no es observable, la spec NO promete verificación automática.
**MUST (RFC2119):**
- MUST-1 permisos array: Given config V2 When se emite `permissions` Then usa array `{action,resource,effect}` con acciones `shell`/`subagent`/`edit` y strings exactos (`git commit *`, `git commit --amend`, `git push *`, `cat **/.env*`, `rm -rf *`).
- MUST-2 `external_directory` global `ask`: Given config V2 When se define Then `external_directory: ask` (V2 lo sube a `allow` por defecto).
- MUST-3 frontmatter `permissions:` en ambas copias: Given el cambio When se aplica Then el frontmatter usa `permissions:` en raíz **y** `templates/` (paridad).
- MUST-4 profundidad vía `subagent`: Given `subagent_depth` ignorado When se traduce Then se reemplaza por permiso `subagent` (advisor primary allow de los 6 + `*: ask`; planner allow `explore`; hojas deny).
- MUST-5 `subtask`→`subagent`: Given commands V1 When se migran Then `subtask:` pasa a `subagent:` en ambas copias.
- MUST-6 `MODEL_RE` con `#`: Given ids `provider/model#variant` When se validan Then `MODEL_RE` acepta `#` en `routine-model.mjs` **y** `init.mjs`.
- MUST-7 docs vivos: Given el cambio When se cierra Then se actualizan `AGENTS.md`, `advisor.md`, `AGENT-PIPELINE.md`, `templates/.opencode/commands/doctor.md`.
- MUST-8 guarda de versión en `--upgrade`: Given `--upgrade` When detecta config V1 Then regenera `opencode.json`.
- MUST-9 `npm test` verde: Given el cambio When corre `npm test` Then verde con paridad raíz↔`templates/`.
**Estrategia:** V2-nativa única; dual V1+V2 **descartada** (V1 y V2 no coexisten → no verificable).
**Traducción por-agente (7):** advisor→primary + permiso `subagent` allow de los 6 (`planner/builder/verifier/critic/summarizer/explore`) + `*: ask` (su `task` pasa a `subagent`); planner→`subagent` allow `explore`; builder/verifier/critic/summarizer/explore→hoja `subagent: deny`.
**Tasks (ordenadas):** 1) Gate 0 empírico (bloqueante); 2) `permissions` array (`shell`) en ambas copias; 3) `external_directory: ask`; 4) `subagent` por-agente (profundidad); 5) `subtask`→`subagent` en commands; 6) `MODEL_RE` con `#`; 7) docs vivos; 8) guarda de versión `--upgrade`; 9) migrar asserts V1 (`contract-tests.mjs:239-263`/`:256-262`, `doctor.mjs:35-37`, `doctor-checks.test.mjs:60-64`, con paridad de severidad raíz↔plantilla; `test/init.test.mjs:372-380` NO asserta claves V1); 10) `npm test` verde.
**Incógnitas que Gate 0 resuelve:** ¿clave top-level `agent` o `agents`? (determina si el alcance incluye `doctor.mjs`, `contract-tests.mjs` y fixtures `doctor-checks.test.mjs`); ¿existen actions `list`/`todowrite` en V2?; ¿`instructions` resuelve?; ¿existe `opencode debug config`?

## 2026-10-18 — EOL canónico al instalar (.gitattributes + render normalizado) ✓

topic: installer/eol-canonical
**Goal:** eliminar las 40+ warnings "LF will be replaced by CRLF" del commit inicial del instalador y, sobre todo, blindar los `.sh` (hook post-commit, check-memory-limits) contra conversiones CRLF de git que rompen bash (`\r: command not found`).
**Discoveries:** la regla existía declarada en `.gitattributes` de la raíz pero NO se aplicaba al escribir: `renderFile` volcaba tal cual (un template CRLF del working tree aterrizaba crudo en el destino) e `installGitHook` usaba `copyFileSync` byte-exacto. El catch-all de `renderTree` dejaba fuera `gitignore`/`.gitattributes`/`.cmd`/`.bat` (sin extensión o ext no listada). Diagnóstico verificado empíricamente: solo los `.ps1` tenían CRLF en disco (canónico ya); el resto del arbol estaba limpio — el riesgo era el working tree de OTRO contribuidor, no este.
**Accomplished:** (1) `canonicalEol()` en `init.mjs` (espejo literal del `.gitattributes`: todo→LF, `ps1|cmd|bat`→CRLF), aplicado en `renderFile`; (2) `installGitHook` normaliza a LF al instalar; (3) `renderTree` rutea por render todo lo textual + los 2 renombres; (4) nueva plantilla `templates/gitattributes` (TEMPLATE_RENAME) que declara la convención en CADA proyecto instalado; (5) `gitInitAndCommit` fija `core.autocrlf=false` LOCAL en repos fresh (best-effort, nunca global); (6) contrato nuevo `eol templates` (44 ficheros) en contract-tests; (7) test nuevo `test/eol-canonical.test.mjs` (3 tests, fixture envenenado con CRLF/LF mixto); (8) `.gitattributes` en catálogos de init.mjs (BACKUP_ITEMS/REGENERATED/PART_HARNESS/uninstallPlan), `TEMPLATE_ONLY_EXACT` y listas de init.test/e2e.
